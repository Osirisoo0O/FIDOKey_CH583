## T1 设备识别

**操作**

1. 插入设备
2. 打开设备管理器（`devmgmt.msc`）
3. 看串口输出

**预期**

- [ ] 设备管理器中出现在 **人机接口设备** 下，硬件 ID 含 `VID_1A86&PID_E008`
- [ ] **没有** 黄色感叹号、**没有** 代码 43 / 代码 10
- [ ] 串口输出：

```
--- selftest ---
AES    = 0
SHA256 = 0
ECDSA  = 0
STORE  = 0
CBOR   = 0
passed 5/5
```

**失败排查**

| 现象 | 可能原因 |
|---|---|
| 代码 43 | 枚举失败。先确认串口有没有打印 `passed 5/5`：**有**说明 CPU 在跑、问题在 USB 层；**没有**说明卡在初始化 |
| 串口无输出 | 串口接错引脚（应为 PA9）、波特率不对、或固件没跑起来 |
| 某项自测非 0 | 那个负值对应该项内部的第几步检查，可直接定位 |

## T2 CTAPHID 底层命令

```bash
python tools/fido2_ctaphid_test.py
```

**逐项预期**

### T2.1 CTAPHID_INIT

- [ ] 响应 **17 字节**
- [ ] `nonce`（前 8 字节）与请求**逐字节一致**
- [ ] `newCID` 为 `00000000`（表示不分配新通道，主机继续用原 ChannelID）
- [ ] 协议版本 `== 2`
- [ ] `caps` 含 `0x04`（CBOR 能力位）

### T2.2 CTAPHID_PING —— **最值得跑的一项**

脚本发 **100 字节** payload。

- [ ] 回显仍是 **100 字节**，且内容逐字节一致

**为什么这项最关键**：HID 单帧只能装 57(初始帧)/59(续帧) 字节，100 字节**必须走多帧**。
它一次性验证了**多帧接收重组**与**多帧发送分片**两条通路——而注册响应约 185 字节也依赖同一套逻辑。

### T2.3 CTAPHID_WINK

- [ ] 返回**空响应**（0 字节）

### T2.4 未定义命令（0x7A）

- [ ] 被拒绝：返回 `CTAPHID_ERROR + 0x01`，或库抛异常（两者都算通过）

### T3 CTAP2 GetInfo

- [ ] `versions` 含 `"FIDO_2_0"`
- [ ] `aaguid` 长度 **16**
- [ ] `options` 里有 `up: True`
- [ ] **没有** `rk`（本实现不支持可驻留凭证，声明了反而会让主机发起不支持的操作）

**失败排查**

| 现象 | 可能原因 |
|---|---|
| PING 回显长度不对 | 多帧分片/重组有 bug（这是 3.1 的核心，重点查） |
| 找得到设备但命令超时 | 主循环没在跑 `ctaphid_process()`，或被浏览器独占（关掉浏览器重试） |
| GetInfo 缺字段 | `ctap_build_get_info()` 的编码问题 |

## T4 MakeCredential（注册）

### 方式 A：脚本

```bash
python tools/fido2_cred_test.py
```

**操作与预期**

1. [ ] 运行后设备 **LED 开始慢闪**（表示正在等待用户确认）
2. [ ] **按下 PB4** → LED 转为快闪
3. [ ] 脚本打印 `[PASS] 注册成功`，且：
   - [ ] `UP 标志 : True` ← **这一位为 True 才说明按键确实生效了**
   - [ ] `AT 标志 : True`
   - [ ] `fmt` 应为 `none`
   - [ ] `credId 长度` 为 32

### 方式 B：浏览器

1. Chrome/Edge 打开 `https://webauthn.io`
2. 输入用户名 → 点 **Register**
3. 出现提示时 **按 PB4**

- [ ] 注册成功，页面显示该凭证

### 预期中的"失败"（也是测试点）

- [ ] **勾选 resident key / 可驻留凭证** 后再注册 → 应失败并返回 `UNSUPPORTED_OPTION (0x2B)`
      —— 这是**如实拒绝**，不是 bug（我们确实没实现 rk）

**失败排查**

| 现象 | 可能原因 |
|---|---|
| LED 不闪，直接失败 | 没走到 UP 闸门；或 `ctaphid_reprocess` 有问题 |
| LED 闪了但按键无反应 | 按键没接在 PB4，或按下时没拉低（用万用表量） |
| 按键后仍失败 | 检查 `auth_sm` 是否收到 GRANTED；可临时把 `SK_LOG_ENABLE` 设为 1 看日志 |
| 浏览器报 `NotAllowedError` | 多半是超时或用户取消 |

## T6 复位与异常路径

### T6.1 快速插拔

- [ ] 连续插拔 USB **5 次**，每次都能重新枚举成功、自测仍 `passed 5/5`

**为什么要测**：USB 复位时 `ctaphid_reset()` 会清挂起标志，而 `auth_sm` 可能还在等按键。
我们专门修过这个「半挂起」隐患——如果没修好，拔插一次后 LED 会一直慢闪、状态卡死。

### T6.2 UP 等待中途拔 USB

1. 发起一次注册（等 LED 慢闪）
2. **在等待期间直接拔掉 USB**
3. 重新插入

- [ ] 设备正常枚举
- [ ] **LED 不再常闪**（若仍在慢闪说明悬空等待没被收掉）

### T6.3 取消操作

1. 发起一次注册，等 LED 慢闪
2. 在浏览器/脚本侧**点取消**（或发 `CTAPHID_CANCEL`）

- [ ] 设备 LED **立即**回到 READY（常亮），**不等 15 秒超时**
- [ ] 之后再发新请求能正常工作

### T6.4 超时

1. 发起注册后**什么都不做**

- [ ] 约 **15 秒**后失败，返回 `ACTION_TIMEOUT (0x3A)`
- [ ] LED 转为错误态（闪几下）

## T7 压力测试（5.4）

- [ ] 连续注册 **20 个**不同用户名的凭证（验证 62 个槽位够用、无越界）
- [ ] 连续登录 **50 次**（验证 signCount 递增、Flash 反复擦写不出错）
- [ ] 插拔 **100 次**（验证枚举稳定性）
- [ ] 长时间通电 **≥ 24 小时**，期间反复操作，观察是否出现卡死

> ⚠️ 已知耐久性限制：当前 `signCount` **每次登录都会擦写 2 页 DataFlash**，
> 按约 10 万次擦写寿命估算，**单个凭证槽约 5 万次登录后可能失效**。
> 计划 5.5 会把它改成页内追加（擦除频率降约 64 倍）。做压力测试时请留意这个量级。

## 附：出问题时怎么给反馈

请提供这三样，能快速定位到具体一层：

1. **完整串口输出**（从上电第一行开始）
2. **失败的那一步 + 报错原文**（脚本的 traceback 或浏览器控制台错误）
3. **LED 表现**（常亮 / 慢闪 / 快闪 / 灭 / 闪几下）

另外，临时开启详细日志有助于定位（`include/debug_log.h` 里把 `SK_LOG_ENABLE` 改成 `1`），
它会在按键变化、UP 等待/授予/超时、挂起重放、CTAP 命令收发等关键点打印。
**测完记得改回 `0`**——`PRINT` 是阻塞串口输出，开着会影响 USB 时序。

## 附二：测试中发现的问题（已修）

### 问题 0（最后一个卡点）：浏览器登录报 Invalid signature

**现象**：注册成功，登录报 `Authentication failed: Could not verify authentication
signature` / `Invalid signature`。设备签名本身在数学上完全正确——脚本里用注册
公钥可以验证通过。

**根因**：**签名编码格式**。

| 层 | 规范 | 格式 |
|---|---|---|
| 设备 ↔ 主机（CTAP2 / COSE） | FIDO CTAP2 / RFC 8152 | **raw `r‖s`**（64 字节） |
| WebAuthn API → 服务端 | WebAuthn Level 2 | **ASN.1 DER** |

按规范，DER 转换是主机（Windows/Chrome）的职责。但本平台上**实测该转换没有发生**：
设备返回 raw 时浏览器/服务端一律报签名无效。改为**设备直接输出 DER** 后，
`webauthn.io` 与 `demo.yubico.com` 两个站点均正常注册与认证。

**为什么脚本能通过、浏览器不能**：`fido2` 库的 `ES256.verify` 把 signature 直接
交给 `cryptography`（期望 DER），即**库假定拿到的是已转换的 DER**。脚本里是我
们手工做的 raw→DER 转换，所以通过；浏览器链路没做转换，所以失败。

**修法**：`src/ctap.c` 新增 `ctap_sig_raw2der()`，把 64 字节 raw 转成
`SEQUENCE { INTEGER r, INTEGER s }`，用 `SK_SIG_DER` 开关控制（默认 1 = DER）。

**DER 编码的坑**：INTEGER 是**有符号**的，`r`/`s` 最高位为 1 时须补 `0x00`
否则被解成负数。本设备的 `r` 实测常以 `0xB6` 这类值开头，正好命中。
实现已与 `cryptography` 的 `encode_dss_signature()` 逐字节核对一致。

> **切换**：`-D SK_SIG_DER=0` 回到规范的 raw。注意 `fido2`
> 脚本在 DER 模式下必然失败（库会再转一次），需要用脚本验证时切回 raw。



### 问题 1：python-fido2 报「发现 0 个 CTAPHID 设备」

**现象**：设备能被 Windows 枚举、串口自测 `passed 5/5`、按键也正常，
但 `CtapHidDevice.list_devices()` 返回空。

**根因**：**HID 报告描述符的 Usage Page 不对**。

原描述符抄自 WCH `HID_CompliantDev` 例程，用法页是厂商自定义的 `0xFF00`：

| 位置 | 原值 | 应为 | 含义 |
|---|---|---|---|
| Usage Page | `0xFF00` | **`0xF1D0`** | FIDO Alliance 专用用法页 |
| Input 的 Usage | `0x02` | **`0x20`** | Input Report Data |
| Input 标志 | `0x81, 0x06` | `0x81, **0x02**` | Data, Var, **Abs** |
| Output 的 Usage | `0x02` | **`0x21`** | Output Report Data |
| Output 标志 | `0x91, 0x06` | `0x91, **0x02**` | Data, Var, **Abs** |

**影响范围比测试脚本更大**：主机侧（Chrome / Windows / python-fido2）都按
**Usage Page == 0xF1D0** 筛选 FIDO 设备。用法页为 0xFF00 的设备**根本不会被认成安全密钥**——
不只是 python-fido2 列不出来，浏览器同样认不出。
（设备描述符与接口描述符本身是合规的，所以设备管理器里看起来一切正常，
这也是它容易被忽略的原因。）

**为什么之前的测试没暴露这个问题**：
- 上电自测（AES / SHA256 / ECDSA / STORE / CBOR）验的是**设备内部逻辑**
- 按键测试验的是 **GPIO 与官方 KEY 服务**
- 两者都**不涉及"主机能否把它识别为 FIDO 设备"**

**修复**：报告描述符改为 CTAP 2.3 11.2.4 规定的 FIDO 用法页版本。
长度仍是 **34 字节**，与配置描述符里声明的 `wDescriptorLength(0x0022)` 一致，
因此配置描述符无需改动。

新描述符 hex：

```
06D0F10901A101092015002600FF750895408102092115002600FF750895409102C0
```

**教训**：这是典型的「**内部逻辑全对、外部契约不对**」。
凡是与主机交互的描述符/协议，都应尽早做一次**端到端识别测试**——
也就是本清单在 T2 之前，其实应该先确认"设备能被 `list_devices()` 列出来"。
