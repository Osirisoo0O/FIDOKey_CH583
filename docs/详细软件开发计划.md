## 阶段二：核心加密与安全模块

### 2.1 硬件随机数生成器
- [x] ~~初始化CH583的TRNG（真随机数发生器）~~ → **实测 CH583 没有 TRNG**，改为多源混合熵（见下）
- [x] 实现`get_random_bytes()`函数，用于生成：
  - 私钥种子
  - 挑战值随机数
  - 加密盐值

  > ⚠️ **方案修正**：原计划假设 CH583 有硬件 TRNG，实测**没有**——
  > `Peripheral/ch58x/` 全目录（inc + src）没有任何 RNG 寄存器定义，`CH58x_common.h`
  > 引入的外设模块（clk/uart/gpio/i2c/flash/pwr/pwm/adc/sys/timer/spi/usbdev/usbhost）
  > 里也没有 RNG；芯片宣传的安全特性同样只有 AES-128 + 芯片唯一 ID。
  >
  > 因此在 `src/app_crypto.c` 中改用**多源混合熵**：
  > 1. `tmos_rand()` —— BLE 库伪随机（由 SysTick 播种）
  > 2. **ADC 内部温度传感器采样抖动** —— 本方案新增的物理熵来源（`rng_adc_noise()`，采样 8 次取低位）
  > 3. `SYS_GetSysTickCnt()` —— 调用时刻的时钟抖动
  > 4. 递增计数器 —— 保证重复调用不会得到相同序列
  >
  > 混合后经两轮 xorshift32 扩散再输出。
  >
  > 🚨 **安全边界（重要）**：这不是密码学安全的真随机源。FIDO2 私钥的熵质量
  > **上限取决于 `tmos_rand()` 的熵池**，而不取决于本函数。正式商用或提交 FIDO 认证前，
  > 应评估外挂安全元件（SE）或改用带硬件 TRNG 的芯片型号。

### 2.2 AES-128加密/解密
- [x] 确认蓝牙库初始化完成后再调用AES模块
  - 用内部闸门实现：`crypto_init()` 置位 `crypto_ready`；未就绪时 `aes_encrypt/aes_decrypt`
    直接返回 `-2`，不会去碰尚未映射好的 BLE 库函数表。
  - 调用顺序由 `peripheral_main.c` 保证：`CH58X_BLEInit()` → … → `crypto_init()`。
- [x] 使用`LL_Encrypt()`和`LL_Decrypt()`函数接口
  - 封装在 `src/app_crypto.c`：`aes_encrypt` / `aes_decrypt`（单块 16 字节）
    + `aes_encrypt_blocks` / `aes_decrypt_blocks`（多块逐 ECB，支持原地 `in == out`）。
- [x] **注意**：AES加解密数据必须保证16字节对齐
  - ⚠️ **这句是推测，WCH 头文件并未写明对齐要求**：`lib/BLE_LIB/CH58xBLE_LIB.h` 中
    `LL_Encrypt/LL_Decrypt` 的注释只有 `@param key/plaintextData/encryptData` 与
    `@return Command Status.`，没有任何对齐或长度说明。
  - 为不依赖该假设，封装统一经 `__attribute__((aligned(16)))` 的静态中转缓冲，
    **无论真实要求是 4 还是 16 字节都满足**。代价：模块**不可重入**，勿在中断中调用。
  - 附带收益：调用方传入未对齐（甚至只读）缓冲区也安全，且支持原地加解密。

  > 🔍 **上电自检**：`crypto_init()` 在 `DEBUG` 构建下会调用 `aes_selftest()`，
  > 用 FIPS-197 附录 B 的已知向量（key=`000102…0f`、plain=`001122…ff`、
  > cipher=`69c4e0d8a7b0430d8cdb78070b4c55a`）同时验证加/解密链路，
  > 串口打印 `AES selftest = 0` 表示通过；失败会关闭 `crypto_ready` 闸门。
  > 烧录后即可用它确认 583 的硬件 AES 是否真的工作。

### 2.3 芯片唯一ID读取
- [x] 读取CH583的唯一ID（`UID`寄存器）
- [x] 将UID作为AES加密密钥的一部分，增强私钥存储安全性
  - 实现 `crypto_derive_storage_key(salt16, key16)`：
    `K = SHA-256( UID(12B) ‖ salt(16B) )` 的前 16 字节（`src/app_crypto.c`），
    为计划 2.5 的安全存储提供密钥派生。

  > ⚠️ **UID 读取的修正**：原代码读的是 `0x1FFFF000`——那是 **CH32V(Cortex-M) 系列**
  > 的系统信息区，CH583(RISC-V) 无此映射，按指针访问会触发总线异常并卡死，
  > 这正是 USB 报「代码 43 / 请求 USB 设备描述符失败」的根因。
  > 已改用 SDK 的 `GET_UNIQUE_ID()`（`CH58x_flash.h`，内部经 `FLASH_EEPROM_CMD`
  > 读 ROM 配置区），写出 8 字节（含 MAC），其余补 0，共 12 字节存入 `g_chip_uid`。详见
  > `USB_Code43_排查总结.md`。

  > 🚨 **顺带发现并重写了完全不可用的 SHA-256**。原先手写的实现在 `src/app_crypto.c`
  > 里有三处致命错误，任何一处都会让摘要值全错：
  > 1. 压缩函数 64 轮**每轮都使用同一个常量 `0x428A2F98`**，而不是 `K[i]`；
  > 2. 填充的长度域按 `pad_len - 4` 定位，正确位置应固定在末尾 8 字节（`pad[60..63]`）；
  > 3. `len % 64 >= 56` 时填充块数不足，且不完整数据块被"补零处理 + 填充阶段"
  >    **重复计算了两遍**。
  >
  > 若直接拿它派生存储密钥，等于把私钥保护建在错的哈希上。已按 FIPS 180-4 重写
  > （含完整 `K[64]` 轮常量表），并新增 `sha256_selftest()`，用三个 NIST 向量自测：
  > `""`、`"abc"`、以及 56 字节串（专门覆盖 `rem >= 56` 需要补两个块的边界）。
  > `crypto_init()` 在 DEBUG 构建下会打印 `SHA256 selftest = 0`，与 AES 自测并列。
  >
  > 🔒 **安全边界**：UID 派生属于"设备绑定"——能防「把 DataFlash 内容整体拷到另一颗
  > 芯片上解密」，但**防不住**「拿到 Flash 内容就能解密」（UID 与盐值都可读出）。
  > 更强方案需要不可导出的主密钥（TRNG 生成 + 受保护区存储），而 CH583 无硬件 TRNG
  > （见 2.1 的记录），此处如实标注该限制。

    并关闭 `uECC_SUPPORT_COMPRESSED_POINT`。实测 **Flash 增量 +7720 字节**。

- [x] **实现核心函数**（`src/app_ecdsa.c` / `include/app_ecdsa.h`）
  - 接口：`ecdsa_generate_keypair` / `ecdsa_compute_public_key` / `ecdsa_sign` /
    `ecdsa_verify`（在原计划的名字上加 `ecdsa_` 前缀，避免与后续模块重名）
  - 数据布局与 CTAP2 的 ES256 / COSE_Key 一致：私钥 32B、公钥 64B（X‖Y，去掉 0x04 前缀）、
    摘要 32B、签名 r‖s 各 32B（**不做 DER 包装**）
  - RNG 经 `uECC_set_rng()` 转发到 `get_random_bytes()`

  > 🔧 **栈大小调整（重要）**：micro-ecc 的临时数组全部在栈上——
  > `uECC_verify`(864B)、`uECC_vli_modInv`(296B)、`uECC_vli_modMult`(384B)、
  > `uECC_sign_with_k_internal`(488B) 的调用链合计约 1~1.5KB，而原栈只有 1024B。
  > 已把 `ldscripts/SecureKey_CH58x.ld` 的 `__stack_size` 由 1024 提高到 **3072**。
  > 调整后 RAM 71.5%，`.bss` 结束于 `0x20004F8C`、栈底在 `0x20007400`，
  > 中间仍有约 9.1KB 空隙，不存在挤压风险。

  > 🔍 **上电自测**：`ecdsa_selftest()` 覆盖 5 组检查，`ecdsa_init()` 在 DEBUG 构建下
  > 打印 `ECDSA selftest = 0`：
  > 1. 私钥 → 公钥 必须匹配 RFC 6979 A.2.5 已知向量（确定性路径）
  > 2. 用**外部已知签名**验证本实现的 `verify`
  > 3. 篡改摘要后验签**必须失败**（负向用例）
  > 4. 本机 `sign` → `verify` 闭环（k 由 RNG 决定，签名值不固定）
  > 5. 现场生成密钥对：由私钥重算公钥须一致，且新密钥也能完成签名闭环
  >
  > 该向量在纳入前已用**独立的 P-256 实现交叉验证**：路径 A（用 r,s 验签，
  > `R.x mod n == r` 成立）与路径 B（用 RFC 6979 的 `k` 反算，r、s 均与记录值一致）。

  > 3. `cbor_skip_item()` 是**迭代实现 + `CBOR_MAX_DEPTH=16` 上限**，不会被恶意嵌套打爆栈
  > 4. 编码侧全部带容量参数 `cap`，越界返回 `CBOR_ENC_ERR` 而不是溢出缓冲区

  > 🔍 **上电自测**：`cbor_selftest()` 共 32 项断言，分 6 组：
  > 基本整数解码、bytes/text、容器跳过（须正好停在末尾）、map 按键查找、
  > **6 个畸形输入负向用例**（截断 / 谎报长度 / 不定长 / float16 / tag / 超 32 位整数）、
  > 编码格式与容量保护、编码→解码往返。
  > `peripheral_main.c` 在 DEBUG 构建下打印 `CBOR selftest = 0`。

### 3.3 `MakeCredential`（注册）命令
- [x] **请求解析**（实现于 `src/ctap.c`）
  - `clientDataHash`：必须恰为 32 字节，否则返回 `INVALID_LEN`
  - `rp`：取 `id` 求 SHA-256 → `rpIdHash`
  - `user`：取 `id` 存入凭证记录
  - `pubKeyCredParams`：检查是否含 ES256（`alg = -7`），否则 `UNSUPPORTED_ALGORITHM`
  - `excludeList`：逐条取出 credId 与已存凭证比对，命中即 `CREDENTIAL_EXCLUDED`
  - `options`：**`rk = true` 时返回 `UNSUPPORTED_OPTION`**（可驻留凭证尚未实现，
    如实拒绝而不是假装支持后让主机拿到不一致的行为）
- [x] **处理逻辑**
  1. 检查 `excludeList`
  2. 生成 ECDSA P-256 密钥对
  3. 私钥经存储密钥加密后写入第一个空槽（**末槽保留给 `secure_store` 自测**）
  4. 构建 `authData` = `rpIdHash(32)` ‖ `flags(1)` ‖ `signCount(4,BE)` ‖ `attestedCredentialData`
  5. credId = 32 字节随机数
  6. 对 `authData ‖ clientDataHash` 求 SHA-256 并用私钥签名
  7. 返回 attestationObject
- [x] **认证方式**：采用 **`none`**（`attStmt` 为空 map）

  > **为什么先做 `none`**：不需要 attestation 证书，浏览器仍能完成注册（只是不显示设备型号）。
  > `authData` 与 credId 已完整按规范构造，将来切到 `packed` 只需填充 `attStmt`，不改动 authData。

  > 🛡️ **写 Flash 之前先验证签名链路**：生成密钥对后立刻做一次 `ecdsa_sign` + `ecdsa_verify`，
  > 两者都成功才写凭证记录。否则一旦写进一把不可用的密钥，主机会反复拿到失败的断言，
  > 而问题要等到 GetAssertion 才暴露；现在失败会在注册这一步就明确报错。

  > 📏 **实测规模**：authData 164 字节，attestationObject ≈ 185 字节 —— **已远超 64 字节 HID 报告**，
  > 必须依赖 3.1 实现的 CTAPHID 续帧才能送达主机。这是多帧支持的第一个真实用例。

  > ⚠️ **RAM 提醒**：本模块静态缓冲合计 1568 字节
  > （authData 256 + attObj 320 + rpIdHash/cdh/credId/priv/pub 224 + 凭证记录 512 + 签名拼接 288）。
  > 编译后 RAM 已达 **78.9%（25848/32768）**，后续 GetAssertion 若再加大缓冲需先核算余量。

### 3.4 `GetAssertion`（登录/断言）命令
- [x] **请求解析**
  - `rpId`：求 SHA-256 → rpIdHash
  - `clientDataHash`：必须恰为 32 字节
  - `allowList`（可选）：**先记住它在报文中的偏移，等所有字段解析完再回扫** ——
    因为 CBOR map 不保证键顺序，`rpId` 完全可能排在 `allowList` 之后
  - `options`：当前跳过
- [x] **处理逻辑**
  1. `allowList` 为空 → 遍历所有槽按 `rpIdHash` 匹配；非空 → 逐条按 `credId` 匹配
  2. 未找到 → `NO_CREDENTIALS (0x2E)`
  3. 取出该槽的私钥密文，用存储密钥解密
  4. 构造 `authData` = `rpIdHash(32)` ‖ `flags(1)` ‖ `signCount(4,BE)` —— **37 字节，不带 attested 数据**
  5. 对 `authData ‖ clientDataHash` 求 SHA-256 并用私钥签名
  6. 返回 credential / authData / signature / user

  > 📐 **签名布局**：CTAP 要求 `r‖s` 连续的 64 字节。`ecdsa_sign()` 的输出是分开的
  > `signature_r` / `signature_s` 两个参数，这里直接传 `s_sig` 与 `s_sig + 32`，
  > 拼起来正好是规范要求的布局，省掉一次拼接拷贝。

  > 📏 **实测响应约 165 字节** → 与 MakeCredential 一样，依赖 CTAPHID 续帧送达。

### 3.5 凭证管理

  - `ctap.c` 已改为复用本模块，删掉了原先重复的两套遍历实现
- [x] 凭证数据结构
  - 已按物理约束实现为 **512 字节定长**的 `ss_cred_t`（见 2.5），字段顺序保证无填充，
    并有编译期断言 `sizeof(ss_cred_t) == 512`

  > **与原计划的差异**：原计划的结构体约 330 字节。但 DataFlash 最小擦除单位是 256B，
  > 槽位必须对齐到擦除单位才能做到"改一条不影响其它条"，故定为 512B（2 页）。
  > 有效载荷未缩水：credId 64 + rpIdHash 32 + user_id 64 + 私钥密文 64 + 公钥 64 + signCount 4。

  > ⚠️ **`credentialManagement` 扩展命令（0x0A）未对外暴露**：

  > 与其提供一个任何人插上就能枚举并删除全部凭证的命令，不如暂不提供。
  > 需要"恢复出厂"时走 `cred_delete_all()`（后续可由长按按键触发）。

- [x] **存储后端抽象（为后续 SPI NOR 迁移铺路）**
  - 新增 `include/storage.h` + `src/storage.c`（注册/分发）+ `src/storage_eeprom.c`（片内实现）
  - `secure_store` 不再直接调用 `EEPROM_*`，一律经后端接口访问
  - 后端需自述 `erase_size` / `capacity`；`secure_store_init()` 会**校验「槽大小是擦除单位的整数倍」**，
    不满足则直接失败，而不是在擦除时静默毁掉同一单元里的其它记录
  - 当前后端：`erase_size = 256`、`capacity = 0x7E00`（已避开 BLE SNV）

  > 🔌 **迁移到 SPI NOR 时的关键点**（已写入 `storage.h` 注释）：
  > 典型 SPI NOR 的 `erase_size = 4KB`，而槽是 512B，不再是整数倍，必须二选一：
  > a) 把 `SS_SLOT_SIZE` 调整为 4096（实现最简单；SPI NOR 容量大，每槽 4KB 通常可接受）
  > b) 实现擦除单元的 read-modify-write（需 4KB 缓冲 —— 当前 RAM 余量下代价不小）
  > 两种做法都**不需要改动上层**（cred_mgr / ctap），只需改后端与槽常量。

  > 🐞 **第一次真机验证发现的问题（已修）**：烧录后串口报 `CBOR selftest = -11`。
  > 定位结果：**是自测自己写错了，不是实现错** —— 第 3 组先 `cbor_read_map()` 读出容器头，

  > `cbor_skip_item()` 的语义（"跳过一个完整数据项"，从容器头调用即跳过整个容器）本身是对的
  > —— `cbor_map_seek` 正是靠它跳过"值"。
  >
  > 修复后用 Python **精确复现该状态机逻辑**验证：新写法 map/arr 分别 `off = 5 / 3`（PASS），
  > 旧写法 `off = 2`（与真机现象吻合）。
  >
  > **教训**：自测本身也需要被验证。此前 AES / SHA-256 / ECDSA 的自测向量都做过独立交叉验证
  > （FIPS-197 / NIST / RFC 6979 / 独立 P-256 实现），唯独 CBOR 这组是"照着实现写测试"，
  > 结果把实现的调用约定想当然地套用错了。5.1 应把"自测自身的正确性"也纳入检查范围。

  > ⚠️ **自测自身也需要被验证（本轮补上的教训）**
  >
  > 第一次真机运行时 `CBOR selftest = -11`，定位发现**是自测自己写错了**：
  > 先 `cbor_read_map()` 读出容器头、**再**调 `cbor_skip_item()`，而 reader 此时已经进到
  > 容器内部，`skip_item` 按定义只跳过一个数据项，offset 自然到不了末尾。
  >
  > 对比各组的向量来源，问题很清楚：
  >
  > | 自测 | 向量依据 | 是否独立验证过 |
  > |---|---|---|
  > | AES | FIPS-197 附录 B | ✅ 真机通过 |
  > | SHA-256 | NIST | ✅ **Python 独立复现比对** |
  > | ECDSA | RFC 6979 | ✅ **独立 P-256 实现交叉验证** |
  > | 安全存储 | 自洽的写-读-还原 | ✅ 真机通过 |
  > | CBOR（原版） | **照着实现写的** | ❌ **无外部依据，于是把调用约定套错了** |
  >
  > 一个写错的自测比没有自测更误导——它会让人以为实现有问题。
  > 因此 5.1 为 CBOR 补了一组**有外部依据**的嵌套向量（第 9 组）：
  > 字节序列按 RFC 8949 手工推导，并用**独立的 Python 解码器**确认「字节 ↔ 期望对象」一致；
  > 该向量还特意覆盖了出错的路径（`cbor_map_seek` 跳过 16B bytes 与嵌套 map）。
  > 新增的 10 项断言（-33 ~ -42）在合入前同样用 Python 模拟 `map_seek` 逻辑验证过
  > （`seek key 4` 停在 array 头、`seek key 2` 停在 text 头，均 PASS）。

### 5.2.2 本轮修复的缺陷（11 项）

**全部为"只有主机真正发起请求时才会暴露"的问题**，此前所有测试（上电自测、按键读取）
都不经过这条路径。

#### 传输层

1. **HID 用法页不是 FIDO 的**（`app_usb.c`）
   报告描述符抄自 WCH `HID_CompliantDev`，用法页是厂商自定义 `0xFF00`。
   主机侧一律按 **`0xF1D0`（FIDO Alliance）** 筛选，因此浏览器与测试工具都认不出设备
   ——不只是列不出来，是根本不会被当成安全密钥。
   修正：Usage Page → `0xF1D0`、Usage → `0x20`/`0x21`、Input/Output 标志 → `0x02`（仍是 34 字节）。

2. **EP1 IN 端点被永久置为 NAK**（`app_usb.c`）
   枚举时主机发 `CLEAR_FEATURE(ENDPOINT_HALT, EP1)`，我们的代码把它实现为
   "把 `UEP_T_RES` 设为 NAK"，**之后无人恢复**。回 NAK 的 IN 事务不会产生 `TOG_BOK`，
   取帧逻辑永远进不去——响应备好了却递不出去（主机表现为卡住）。
   修正：主循环里检测到有响应就主动置 ACK。

3. **主动 ACK 时未先装载缓冲**（`app_usb.c`）
   第 2 项修完后发现主机读到**全 0**：只置 ACK 不填缓冲，主机取到的是空数据
   （ISR 的取帧逻辑在收到 IN 令牌后才跑，那时已太晚）。
   修正：**先装载第一帧，再置 ACK**，用 `ctaphid_ready_to_load()` 判首帧。

4. **缺少 `CTAPHID_KEEPALIVE`**（`ctaphid.c`）
   规范要求等待用户确认期间定期上报 KEEPALIVE。我们没有发，Chrome 约 10 秒后放弃。
   修正：挂起期间每 500ms 上报 `KEEPALIVE(UPNEEDED)`。

#### CTAP 协议层

5. **CTAP2 响应缺少状态码前缀**（`ctaphid.c`，3 处）
   响应格式应为 `[status(1B)] + [CBOR]`，成功路径却把 CBOR 直接放在首字节，
   主机把 `0xA4`（map 头）当成了状态码。
   **失败路径反而是对的**，所以只有成功路径受影响。
   修正：`ctaphid_process()` / `ctaphid_reprocess()` / `ctaphid_ctap_reply()` 三处
   改为把 CBOR 写到 `tx_buf + 1`，长度 +1。

6. **CBOR 嵌套 map 的键类型错误**（`ctap.c`，5 处）
   **编码规则是分层的：顶层请求用整数键，嵌套结构用文本键。**
   顶层用 `cbor_read_uint()` 正确，但嵌套层也用了它——`cbor_read_uint` 遇到
   `0x63`（text 头）直接报 `CBOR_ERR_TYPE`，冒泡成 `INVALID_CBOR`。
   `ctap_check_options()` 是唯一写对的（用 `cbor_read_text`）。
   修正：`ctap_parse_rp` / `ctap_parse_user` / `ctap_check_algs` /
   `ctap_check_exclude_list` / `ctap_get_assertion` 的 allowList 元素，键改为按文本读取。

7. **`GetAssertion` 响应的 `credential` 与 `user` 用了整数键**（`ctap.c`）
   这两者是**嵌套结构**，应为文本键（`"id"` / `"type"`）。
   用整数键时主机按 `"type"` 取值拿到 bytes，报"数据类型无效"（`0x8007070C`）。
   **注册响应不受影响**，因为它的 `{1: fmt, 2: authData, 3: attStmt}` 全是顶层整数键。
   修正：改为 `"id"` / `"type"` 文本键。

8. **`user.id` 被 `memset` 清零**（`ctap.c`）
   `ctap_parse_user()` 会把 `user.id` 写进 `s_rec.user_id`，但清零动作在
   "落盘"阶段才做——把刚解析出的内容抹掉，只从栈变量补回了**长度**。
   结果存进 Flash 的 `user.id` 全为 0，登录时主机判定响应无效。
   修正：`memset(&s_rec, ...)` 提前到**参数解析之前**。

9. **`options.up = false` 时仍强制等待按键**（`ctap.c`）
   浏览器做条件式 UI / 自动填充探测时会发 `up=false` 的 `GetAssertion`，
   我们却傻等 15 秒，网页表现为"无响应"。
   修正：`ctap_up_gate(need_up)` 支持跳过；**闸门位置后移**到参数解析之后
   （`need_up` 只能从 `options` 得知），`GetAssertion` 的闸门更放到
   "确认存在匹配凭证之后"，避免无凭证时白等。

#### 应用层 / 其他

10. **LED 从未工作过**（`LED.h` / `auth_sm.c` / `main()`）
    三个叠加：(a) `HAL_LED` 为 `FALSE`，`HAL_LedInit()` 从未编译；
    (b) `HAL_LedInit()` 里留有官方示例 `HalLedBlink(HAL_LED_1, 10, 30, 4000)`，
    上电后自行闪约 40 秒；(c) **`LED1_BV = BV(15)` 与实物不符，本板 LED 在 PB18**。
    修正：`-D HAL_LED=TRUE`、清掉示例闪烁、`LED1_BV` 改为 `BV(18)`（引脚由扫描程序实测确定）。

11. **`auth_sm_init()` 不设置 LED**（`auth_sm.c`）
    只清软件状态，LED 停在 `HAL_LedInit()` 设的 OFF，上电后像是坏了。
    修正：复用 `auth_sm_clear()`（清状态并置为就绪常亮）。

### 5.2.3 已解决：浏览器登录签名验证失败

**最终结论：浏览器链路不会把 CTAP2 的 raw `r‖s` 转成 ASN.1 DER，设备必须直接输出 DER。**

#### 现象与定位过程

1. `webauthn.io` **注册成功**，登录报
   `Authentication failed: Could not verify authentication signature` / `Invalid signature`
2. 设备侧排查：用注册公钥**独立验证登录签名 → 通过**（脚本里手工做了 raw→DER 转换）
3. `tools/fido2_server_test.py` 走 `register_complete` + `authenticate_complete`
   **两项全通过** → 设备侧密码学逻辑与响应结构均无误
4. 关键对比：**同样的输入，手工验证（含 raw→DER）通过，而把 raw 直接交给
   `fido2` 的服务端验证失败**。`fido2` 的 `ES256.verify` 直接把 signature 交给
   `cryptography`（期望 DER），说明**库假定自己拿到的是已转换的 DER**
5. 改固件直接输出 DER 后，**`webauthn.io` 与 `demo.yubico.com` 两个站点均可正常注册与认证**

#### 规范层面的说明（重要）

| 层 | 规范 | signature 格式 |
|---|---|---|
| 设备 ↔ 主机（CTAP2） | FIDO CTAP2 / COSE (RFC 8152) | **raw `r‖s`** |
| WebAuthn API → 服务端 | WebAuthn Level 2 | **ASN.1 DER** |

**按规范，DER 转换是主机（Windows/Chrome）的职责**，所有真实密钥（YubiKey 等）
返回的都是 raw。但本平台上实测该转换没有发生 —— 这可能与 Windows 的 FIDO 栈
或 Chrome 的 WebAuthn 后端实现有关（未进一步确认根因）。

**因此本实现在规范层面做了一个让步**：设备直接输出 DER。

#### 实现与开关

```c
/* src/ctap.c */
#ifndef SK_SIG_DER
#define SK_SIG_DER                  1     /* 1 = DER（当前默认）；0 = raw（规范行为）*/
#endif
```

- 新增 `ctap_sig_raw2der()`：纯 C 的 raw `r‖s` → DER 转换
- **实现已核对**：与 `cryptography` 的 `encode_dss_signature()` **逐字节一致**，
  覆盖 `r` 最高位为 1（需补 `0x00`）这一 DER 编码最易错的情况
- 缓冲新增 `s_sig_der[80]`（DER 最长 74 字节）
- `MakeCredential` 不受影响（`attestation = none`，响应中本无签名）

#### 副作用与风险

| 项 | 说明 |
|---|---|
| **`fido2` 脚本会失效** | 库期望 DER 输入并会**再转一次**，故 `fido2_cred_test.py` / `fido2_server_test.py` 在 DER 模式下必然失败。切回 `-D SK_SIG_DER=0` 即恢复 |
| **非规范行为** | 其他客户端（libfido2 / 某些浏览器或 OS）可能期望 raw。若换平台测试，先用 `SK_SIG_DER=0` 对照 |
| **后续建议** | 若日后确认某个平台确实做转换，可考虑按平台/按客户端能力动态选择；目前无此信息，保持开关即可 |
